Study protocol

Explain, predict, discriminate, diagnose

Explain

State the invariant without jargon, then map every role to a Kubernetes component or object.

Predict

Given one write or failure, predict the next API object, queue, controller, node, or packet transition.

Diagnose

Name evidence that distinguishes competing causes. A command list without a hypothesis is not a strong answer.

For every answer: identify the authority, the asynchronous boundary, the convergence mechanism, and one discriminating failure signal.

Module 1

The control plane is an asynchronous state machine

The API server owns the contract and etcd persists API state. Controllers create and repair intent. The scheduler binds Pods. Kubelets turn assignments into node-local reality.

API write
Persist canonical object
Controllers create dependents
Scheduler binds Pod
Kubelet realizes it

kube-apiserver

The HTTP API and policy boundary. Components coordinate through it rather than reading etcd directly.

etcd

A strongly consistent Raft-backed store for API-server data. Quorum and latency affect the entire control plane.

Scheduler, controllers, kubelet

Controllers decide what objects should exist, the scheduler chooses a node, and kubelet executes the assigned Pod.

Invariant: no component “runs a Deployment.” Several independent loops advance distinct API objects until a kubelet has enough durable intent to start containers.

  • Cluster ArchitectureThe upstream component map and control-plane/node boundary.
  • Kubernetes ComponentsFast role-by-role reference for every core component.
  • Control-plane communicationWhich direction connections travel and where the API server mediates.
Who starts a container after a Deployment is created?

Strong answer:

The Deployment controller creates a ReplicaSet. The ReplicaSet controller creates Pods. The scheduler binds each Pod. The selected node's kubelet then asks the runtime to create its sandbox and containers.

What survives a control-plane outage?

Strong answer:

Existing processes and programmed data paths may continue. API writes, placement, repair, endpoint changes, leases and most day-two actions degrade. “Traffic still flows” does not mean the cluster is healthy.

Why should a controller not read etcd directly?

Strong answer:

It would bypass authentication, authorization, admission, defaulting, validation, conversion, audit, versioning, and supported watch semantics while coupling itself to storage representation.

Module 2

Trace every API request through policy and persistence

A request is authenticated, authorized, admitted, defaulted and validated before persistence; audit and flow control surround that path. Reads and watches then expose canonical API state to clients.

Authenticate identity
Authorize attributes
Mutate / default
Validate / admit
Persist + notify watches

Authentication vs authorization

Authentication establishes user and groups. Authorization decides whether that identity may perform the verb on the resource or non-resource path. RBAC grants permissions; it does not authenticate.

Admission

Mutating admission may change an object; validating admission may accept or reject it. Webhooks add network and certificate dependencies to the API request path.

Optimistic concurrency

resourceVersion protects updates against stale state. Controllers should refetch and recompute after conflicts rather than blindly overwrite.

Server-side apply

Managed fields record ownership of field paths. Conflicts are ownership signals, not errors to suppress with unconditional force.

Webhook failure analysis

  • Scope rules and object selectors: should this request call the webhook?
  • Service endpoints, DNS, TLS trust, timeout, and API-server reachability.
  • failurePolicy: fail closed for safety or fail open for availability is a domain decision.
  • Mutation idempotency and reinvocation; validation must be deterministic and fast.

Why can one admission webhook stall unrelated deployments?

Strong answer:

If its rules match broadly, each API request synchronously depends on the webhook Service, TLS, and response deadline. Failure policy determines whether timeout rejects or bypasses the request.

RBAC allows the request, but it is still rejected. What layers remain?

Strong answer:

Admission policies/webhooks, schema validation, quotas, immutable-field rules, API conversion, and storage failures remain. A successful authorization decision only clears one gate.

What is the safe response to an update conflict?

Strong answer:

Fetch the latest object, recompute the desired delta, and retry with bounded backoff. Overwriting stale state can destroy another writer's changes.

Module 3

Reconciliation makes unreliable events safe

Events schedule work. A controller reads current state, compares it with intent, and takes an idempotent step toward convergence.

List + resourceVersion
Watch changes
Cache objects
Queue stable key
Reconcile latest state

List-watch recovery

A list establishes current state and a collection resource version. Watches stream later changes. On expired history, relist and resume.

Level-based behavior

Correctness comes from recomputing what should be true now, not replaying every historical transition.

Rate-limited queue

Handlers enqueue namespace/name keys; workers fetch current objects. Burst deduplication and backoff isolate producers from retries.

External side effects

Use stable external idempotency keys, observe before create, persist provider identity, and make every phase resumable.

  • client-go informer/cache APIPrecise SharedInformer, reflector, cache, and notification contracts.
  • Kubernetes sample-controllerUpstream code showing informer, workqueue, and sync-handler wiring.

Why queue a key instead of an event payload?

Strong answer:

A key deduplicates bursts and makes the worker read current truth. Payloads preserve stale intermediate states and encourage fragile event-replay logic.

A watch event is lost. Is correctness lost?

Strong answer:

Not in a correct controller: relist/reconnect, resync or related changes schedule reconciliation, which compares current levels. Events improve latency, not correctness.

What causes a controller hot loop?

Strong answer:

It writes on every pass even when semantic state is unchanged, triggering its own watch repeatedly. Compare before patching and avoid status timestamps or reordered fields that always differ.

Module 4

Workload controllers encode different lifecycle promises

Deployments, StatefulSets, DaemonSets, Jobs, autoscalers, and disruption controls are distinct state machines—not interchangeable YAML wrappers.

Deployment

Manages ReplicaSets for replaceable Pods and controlled rollouts using surge, unavailability, readiness, and progress conditions.

StatefulSet

Adds stable ordinal identity, ordered lifecycle, and per-Pod claims. It does not make the application itself replicated or consistent.

DaemonSet and Job

A DaemonSet targets eligible nodes; a Job targets successful completion. Their replacement and retry semantics solve different invariants.

Autoscaling: HPA changes replica count from metrics; VPA recommends or changes resource requests. If both act on CPU or memory requests, the denominator can move beneath HPA. Stateful systems add identity, quorum, storage, and disruption constraints.

Disruption distinctions

A PodDisruptionBudget limits API-initiated voluntary disruption; it does not prevent node failure, OOM, direct Pod deletion, or every controller action. Scheduler preemption selects victims for a higher-priority Pod; kubelet eviction reacts to node pressure.

  • Workload controllersDeployment, StatefulSet, DaemonSet, Job, and ReplicaSet semantics.
  • Horizontal Pod AutoscalingThe control loop, utilization calculation, behavior, and stabilization.
  • Disruptions and PDBsVoluntary versus involuntary disruption and what budgets actually protect.
  • Vertical Pod AutoscalerUpstream VPA components, modes, recommendations, and limitations.
Deployment vs StatefulSet: what is the real discriminator?

Strong answer:

Use StatefulSet when stable network and storage identity and ordered lifecycle are part of correctness. “Has a database” is not enough. Explain the application's own replication and failure semantics too.

Can HPA and VPA safely control the same workload?

Strong answer:

They can conflict when VPA changes CPU/memory requests used as HPA utilization denominators. Separate signals—such as HPA on queue depth and VPA recommendations—or constrain update modes and test disruption.

Does a PDB guarantee availability?

Strong answer:

No. It constrains voluntary eviction through the Eviction API. It cannot stop involuntary failures and is only useful alongside replicas, readiness, topology, and adequate capacity.

Module 5

CRDs are public APIs; operators give them behavior

A CRD registers a resource and schema, a CR is one stored object, and a controller reconciles it. Long-lived APIs require compatibility, conversion, ownership, and deletion design.

CRD registers GVK
API validates CR
Controller observes
Children / external state
Status reports

Spec and status

Spec is intent. Status is observation, including conditions and observedGeneration. A controller should not rewrite intent to hide limitations.

Structural schema

Accurate list/map semantics, pruning, defaulting, validation, and server-side apply behavior are part of the API contract.

Served and storage versions

Several representations may be served; one is used for new stored writes. Changing the storage marker does not migrate old objects.

Ownership and deletion

Owner references guide garbage collection. Finalizers hold an object after deletion request until the owning controller completes cleanup.

CRD, CR, controller, operator: distinguish them.

Strong answer:

The CRD registers an API kind. A CR is one instance of that kind. A controller reconciles state. An operator packages a controller with domain lifecycle knowledge, RBAC, installation and upgrades.

Can you switch storage to v2 and immediately remove v1?

Strong answer:

No. Serve both, verify conversion and round trips, switch new storage, migrate existing objects, inspect stored versions and client use, then retire v1.

A CR is stuck Terminating. Remove its finalizer?

Strong answer:

Only after identifying its owner and proving cleanup completed or was safely performed elsewhere. Blind removal can leak external resources and violate invariants.

Module 6

Scheduling is constraint solving under changing information

The scheduler queues unscheduled Pods, filters infeasible nodes, scores candidates, reserves state, permits or rejects, and records a binding. Kubelet—not scheduler—then executes.

Queue
PreFilter / Filter
Score
Reserve / Permit
Bind

Hard vs soft placement

Resources, required affinity, taints, ports, volume topology, and policy may filter. Preferences and scoring rank remaining nodes.

Requests are scheduling currency

Placement uses declared requests, not live usage. Bad requests create overcommit, low utilization, or node pressure later.

Priority and preemption

Priority orders work and may allow a pending Pod to displace lower-priority victims. The nominated node is still a proposal, not a guarantee.

Eviction

Kubelet eviction responds to local pressure using usage relative to requests, priority, and pressure signals. It is distinct from scheduler preemption.

Why is a Pod Pending when CPU appears free?

Strong answer:

Check requests against allocatable capacity plus affinity, taints, topology spread, ports, PVC topology/capacity, quotas, and scheduler events. Observed utilization is not the scheduler's feasibility input.

Preemption vs eviction?

Strong answer:

Scheduler preemption removes lower-priority Pods to make a pending higher-priority Pod schedulable. Kubelet eviction terminates Pods under node pressure; API eviction represents voluntary disruption and honors PDBs.

Why have Reserve and Unreserve phases?

Strong answer:

Stateful scheduler plugins can tentatively claim resources before binding and roll them back if a later phase fails. Unreserve must be idempotent.

Module 7

Kubelet turns a binding into processes, mounts, and probes

The kubelet observes Pods assigned to its node, coordinates runtime, network, storage, secrets, probes, and status, and continuously syncs desired Pod state.

Bound Pod
Volumes + sandbox
CNI network
Images + containers
Probes + readiness

CRI boundary

CRI is the gRPC contract between kubelet and a runtime such as containerd. OCI describes lower-level runtime and image specifications; it is not the kubelet API.

Pod sandbox

The runtime creates an isolation and network namespace anchor before normal containers. CNI configures its network attachment.

Probe semantics

Startup gates liveness/readiness during slow initialization; liveness restarts containers; readiness controls endpoint participation without restarting.

Termination

Deletion starts a grace period, lifecycle hooks and TERM, endpoint removal, and eventual force. Ordering is concurrent and should not be treated as a transaction.

Pod is Running but receives no traffic. Why?

Strong answer:

Running is a phase, not readiness. Inspect readiness gates/probes, container readiness, EndpointSlice membership, Service selection and ports, then the data plane.

CRI vs OCI vs CNI?

Strong answer:

CRI connects kubelet to the container runtime; OCI specifies image/runtime primitives used below that boundary; CNI configures network attachment for the Pod sandbox.

Why can the API show stale Pod status during node failure?

Strong answer:

Status is reported asynchronously by kubelet. Loss of node/API connectivity prevents updates until lease/node controllers infer unreachability and other controllers react.

Module 8

Networking separates Pod reachability from Service identity

CNI attaches Pod networking. EndpointSlices represent ready backends. kube-proxy or an eBPF replacement translates stable Service semantics into a node data plane.

DNS / Service VIP
Node data-plane lookup
Select EndpointSlice backend
Route to Pod IP
Policy + listener

iptables, IPVS, nftables

These are kube-proxy implementations, not different Service APIs. Simple O(N) vs O(1) slogans omit rule update, locality, kernel, and semantic tradeoffs; current clusters may use nftables.

eBPF replacement

An eBPF data plane can implement Service translation and connection tracking in BPF maps, at hooks such as socket or traffic control. It bypasses traditional netfilter, not connection state itself.

Headless Service

clusterIP: None removes VIP proxying and returns endpoint addresses through DNS, moving selection to clients.

Policy and routing

NetworkPolicy declares allowed flows when the plugin enforces it. It does not create routes or prove an application listens.

How a Pod gets its network

A CNI plugin is an executable, not a service. The container runtime, not the kubelet, creates the sandbox’s network namespace. It reads CNI configuration from disk on that node and executes the plugin chain. The operation arrives in CNI_COMMAND and the configuration on stdin. A JSON result returns on stdout describing the IP, routes, DNS and MAC. Allocation is delegated to an IPAM plugin so every interface plugin does not reimplement it. If IPAM fails during ADD, the caller issues DEL to roll back. Each plugin in a chain acts on the same single interface, composing behaviour rather than adding interfaces.

Currency: the maintainer talks describe four operations. CNI 1.1 adds GC and STATUS alongside ADD, DEL, CHECK and VERSION. Products such as Calico and Cilium also run a node agent, but that agent is not the CNI plugin binary.

Service DNS resolves, but ClusterIP times out. Trace it.

Strong answer:

Inspect Service ports and EndpointSlices, test ready Pod IPs, inspect kube-proxy/BPF programming and conntrack, verify routing/MTU/policy, then the target listener.

Does Cilium “remove conntrack”?

Strong answer:

It can bypass netfilter's conntrack path for Service handling while maintaining connection state in eBPF maps. Separate implementation from the need for stateful flow tracking.

CNI vs kube-proxy?

Strong answer:

CNI configures Pod network attachment; kube-proxy implements Service VIP forwarding. A single product may replace both paths, but the contracts and failure questions remain distinct.

Module 9

DNS is resolver policy plus a configured server pipeline

kubelet writes Pod resolver settings. Search expansion and ndots shape queries. The DNS Service reaches CoreDNS, whose compiled handler chain and Corefile configuration answer cluster names or forward upstream.

Application resolver
search + ndots
kube-dns Service
CoreDNS plugins
cluster answer / upstream

Kubernetes plugin

Watches Services and EndpointSlices to synthesize ClusterIP, headless endpoint, and named-port records.

Plugin chain

The Corefile selects and configures plugins, but its textual order does not reorder execution. The binary's plugin.cfg defines chain order; zone selection and plugin behavior determine the resulting path.

Search amplification

Names below the dot threshold may be expanded across search domains before absolute lookup, multiplying NXDOMAINs and latency.

NodeLocal DNSCache

A per-node cache can shorten the path, reduce load and UDP/conntrack pressure, but adds another cache, listener, and configuration surface to diagnose.

PVC is Pending. What evidence distinguishes causes?

Why can a scheduled Pod remain stuck mounting?

Module 11

Availability depends on quorum, replaceability, and rehearsed recovery

API-server replicas are replaceable; etcd members form a consensus group. Leader election protects active writers. Backups are only credible after verified, documented restoration.

Raft quorum

A majority commits writes: floor(N/2)+1. Three and four members both tolerate one failure; odd membership usually buys better fault tolerance per member.

WAL and snapshots

Committed log entries and durable synchronization protect consensus; snapshots compact state. etcd filesystem copies are not a substitute for supported snapshot procedures.

Leader election and leases

Scheduler and controller replicas use leases so one active leader writes while standbys can take over. Node leases provide lightweight liveness signals.

Upgrade and restore

Respect version skew, drain and sequence components, preserve PKI/configuration, verify snapshots, restore to a new data directory, and test application-level recovery.

Why does adding a fourth etcd member not increase failure tolerance?

Strong answer:

Quorum rises from two-of-three to three-of-four, so both tolerate only one failed member. Five members tolerate two failures, at higher replication and coordination cost.

What does an etcd snapshot not contain?

Strong answer:

It captures API state, not necessarily PKI, static Pod manifests, component configuration, external load balancers, container images, CSI data, or cloud resources. Recovery requires the full control-plane context.

How do you prove disaster recovery works?

Strong answer:

Restore a verified snapshot into an isolated environment. Rebuild API access. Validate critical objects and controllers. Then test workload and data recovery against documented RPO and RTO. snapshot status alone proves nothing.

Module 12

Protect the API under load and trace bottlenecks by boundary

Scalability is not one number. API Priority and Fairness protects limited concurrency, while watches, caches, queues, scheduler throughput, etcd latency, logs, metrics, and audit reveal different pressure points.

Priority level

APF

FlowSchemas classify requests into PriorityLevelConfigurations. Limited levels use queues and concurrency seats so noisy clients cannot consume the whole API server.

Watch economics

Informers share list/watch caches. Poor clients that repeatedly list, reconnect, or request huge objects amplify API server and etcd load.

Signals

Request latency/rejections, APF seats/queues, etcd fsync/commit latency, controller queue depth, scheduler attempts, kubelet/runtime latency, and DNS/data-plane metrics isolate layers.

Events are lossy hints, logs are component-local unless shipped, metrics aggregate, audit records API activity, and traces connect a request path. None alone is ground truth.

A controller floods the API. How can APF help—and not help?

Strong answer:

APF can classify, queue, bound or reject its requests while preserving concurrency for critical flows. It cannot fix a hot loop, bad list behavior, huge objects, or overloaded etcd; fix the client too.

Events, logs, metrics, audit: which is authoritative?

Strong answer:

Canonical object state is authoritative for current API truth. Events explain selected transitions, logs explain component decisions, metrics reveal aggregate pressure, and audit records API requests. Correlate them.

Give a 90-second architecture answer.

Strong answer:

Clients declare intent through a policy-enforcing API persisted in etcd. Controllers reconcile objects; the scheduler binds Pods; kubelets coordinate runtime, networking and storage. Services and DNS expose ready endpoints. Every stage is asynchronous, observable, retryable, and protected by ownership, quorum, flow control and recovery mechanisms.

Bootstrap authority

kubeadm creates configuration, credentials, manifests and API bootstrap objects, then exits. The kubelet owns control-plane process continuity.

Module 14 · CKA workloads

Configuration delivery, QoS, eviction and OOM are separate contracts

An object update does not imply process reload. A QoS label does not perform an eviction. Kubelet pressure handling and kernel OOM selection operate at different layers.

ConfigMap and Secret delivery

Environment values are fixed at process start. Projected files refresh eventually; the process must reload them.

QoS

Guaranteed, Burstable and BestEffort are derived from CPU and memory requests and limits.

Kubelet eviction

Proactively fails Pods from pressure signals; hard eviction can bypass normal grace and PDBs.

Kernel OOM

Selects a process/container using memory behavior and oom_score adjustment when memory is exhausted.

Why did a ConfigMap update not change the process?

Strong answer:

Environment delivery requires restart. A mounted projection updates eventually, but the process may cache or never reread it. A Deployment rolls only if its Pod template changes.

Guaranteed QoS means never evicted?

Strong answer:

No. It is least likely under common memory pressure, but node stability can still require eviction. Actual ranking uses usage above requests, Priority and relative excess.

Eviction versus OOM kill?

Strong answer:

Kubelet eviction proactively fails a Pod from node signals. Kernel OOM kills a process after exhaustion; kubelet may restart that container.
