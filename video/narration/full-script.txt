[00 Six things have to go right]
You type kubectl apply. A few seconds later, traffic reaches your application. In between, at least six independent systems have to agree — and each one can fail in a way that looks exactly like the others. A pod stuck Pending. A pod Running but getting no traffic. A service that resolves but times out. Every one of those is a different subsystem, and telling them apart is most of what senior Kubernetes work actually is. So let's follow one declaration all the way down: from a line of YAML, to a packet arriving at your process.

[01 Three lanes]
Hold three lanes. The top lane is the control plane: the API server, etcd, the controllers, the scheduler. It decides what should exist. The middle lane is the node: the kubelet, the container runtime, the network and storage plugins. It makes things real. The bottom lane is the pod itself: its sandbox, its containers, its readiness. These lanes are not a pipeline. They are independent loops that watch each other and retry. No single component drives your deployment from start to finish, so any one of them can stall while the others look healthy.

[02 Stage 1 — The request]
Stage one. You write a spec — a declaration of what you want, not a set of instructions. kubectl serialises it and sends an HTTP request over TLS to the API server. The API server is the only component that talks to storage. Controllers, the scheduler, the kubelet: none of them read etcd. They all coordinate through this one HTTP contract, which is what lets the API server enforce policy on every write. A controller that reads etcd directly skips authentication, authorisation, admission, validation, conversion and audit in one go.

[03 Stage 2 — Five gates]
Stage two: the gauntlet. The request is authenticated — who is this? Then authorised — may they do this? RBAC lives here, and it only grants permissions; it never establishes identity. Then mutating admission, which may change your object: injecting a sidecar, adding a default. Then validating admission, which may reject it. Mutation runs first, so what gets validated is the final object. Only then is it written to etcd and watchers notified. Every gate is a separate reason your apply can fail, and they fail with different messages. When RBAC allows something and it is still rejected, think admission webhooks, schema validation, quota, immutable fields.

[04 Stage 3 — Durable, and only then]
Stage three. The object is written to etcd, and a write is not durable the moment the leader receives it. etcd is a Raft consensus group: a majority of members must commit the entry before the write is acknowledged. Floor of N over two, plus one. Three members tolerate one failure, and adding a fourth buys nothing — quorum rises with it. Five is the next size that helps. Your pod now exists only as a record in a database. Nothing is running. Nothing has been scheduled. You have declared intent, and that is all.

[05 Stage 4 — Controllers, plural]
Stage four. Controllers notice — not one controller, several, chained. The Deployment controller sees a Deployment with no matching ReplicaSet and creates one. The ReplicaSet controller sees a ReplicaSet with fewer pods than it wants and creates pods. Each watches the API, compares what exists against what was declared, and takes one idempotent step to close the gap. That comparison is level-based: it asks what should be true now rather than replaying a history of events. So a dropped watch event costs latency, never correctness — the next reconcile recomputes from current state and gets the same answer.

[06 Stage 5 — Filter, then score]
Stage five. The pods exist, but no node is assigned. The scheduler runs two distinct phases. Filtering: which nodes could run this at all? Requests against allocatable capacity, taints, node affinity, topology constraints, volume topology, free host ports. Nodes that fail are eliminated outright. Then scoring: of the survivors, which is best? Spread, resource balance, preferences. Filtering uses your declared requests, not what your pods are actually using. A cluster can sit at fifteen percent measured CPU and still refuse to schedule, because every pod requested far more than it needs. When a pod is Pending, dashboards showing free capacity are not evidence.

[07 Stage 6 — A name, written down]
Stage six, and it is smaller than it sounds. The scheduler does not place the pod on the node. It does not contact the node. It does not start anything. Its entire output is a binding — one API write that sets the pod's nodeName field. The decision is now a fact in the database, and the scheduler moves to the next pod. Everything that follows is somebody else's job, triggered only because a kubelet was watching for pods with its own name on them.

[08 Stage 7 — The node notices]
Stage seven. Control crosses from the control plane to the node. On the chosen machine, the kubelet has a watch open for pods assigned to it. Your pod's nodeName now matches, so it appears. Nobody sent the kubelet a command — it is a sync loop, not a command receiver, and that difference matters when you are debugging. From here its job is to keep driving this pod toward its declared state: coordinating the runtime, the network, storage, secrets, probes, and reporting status back.

[09 Stage 8 — The sandbox]
Stage eight. The kubelet calls the container runtime over CRI, a gRPC contract, and the boundary the kubelet actually speaks across. The runtime creates the pod sandbox first, before any of your containers. The sandbox holds the namespaces your containers will share — network, IPC — anchored by a tiny pause container that runs no application code. The network has to belong to something before a container can join it, so you can have a healthy runtime and a pod with no networking.

[10 Stage 9 — CNI wires it up]
Stage nine. The runtime — not the kubelet — sets up networking. It reads CNI configuration from disk on that node and executes a plugin. A CNI plugin is not a daemon. It is a binary the runtime runs: the operation arrives in an environment variable, CNI underscore COMMAND, set to ADD. The configuration arrives on standard input. The plugin creates and wires the interface inside the sandbox's namespace and returns a JSON result on standard output. Address allocation is delegated further, to an IPAM plugin, which hands back the IP, the gateway and the routes for the main plugin to apply. So a pod's IP comes from an IPAM plugin, invoked by a CNI plugin, invoked by the runtime — not the kubelet, and not the API server.

[11 Stage 10 — Images and processes]
Stage ten. Now the images. If a layer is already on the node it is reused; otherwise it is pulled from the registry. The containers are created inside the sandbox that already exists, joining its namespaces. Below CRI, containerd calls a lower-level runtime, runc, and this is where OCI lives: the specification for the image format and for creating namespaces and cgroups around a process. The kubelet speaks CRI, containerd speaks OCI downward, and CNI attached the network. Three contracts, three places to look.

[12 Stage 11 — Running is not ready]
Stage eleven. The process is alive, and the pod's phase becomes Running. Running is not ready. Running means the process started. Ready means the application will accept traffic — and those are separated on purpose. The startup probe gates the others while a slow application boots. The liveness probe restarts the container if it wedges. The readiness probe does something different: it does not restart anything, it controls whether you receive traffic at all. Getting these confused is how a slightly slow dependency turns into an endless restart loop.

[13 Stage 12 — Becoming an endpoint]
Stage twelve, and we go back up to the control plane. The readiness probe passes, the kubelet reports ready, and the EndpointSlice controller notices. It adds your pod's IP to the Service's EndpointSlice — the object that lists which backends are currently able to serve. This is the mechanical reason a readiness probe controls traffic. It is not magic and it is not local: readiness changes an API object, and that object is what every node's data plane reads. Which also means that if your service has no ready backends, the EndpointSlice is empty, and that single fact explains the outage faster than any packet capture will.

[14 Stage 13 — The data plane]
Stage thirteen. On every node, something watches that EndpointSlice and programs the local data plane so traffic to the Service's virtual address reaches a real pod IP. Classically that is kube-proxy, writing iptables or IPVS or, in current clusters, nftables rules. An eBPF data plane does the same job differently — translating the address at the socket layer, before packets are built, and keeping connection state in its own maps rather than netfilter's. eBPF does not remove connection tracking; it moves where the state lives. And the Service contract does not change when the backend does. These are implementations, not APIs.

[15 Stage 14 — The packet]
Stage fourteen. A client resolves your service name — and even that has a subtlety, because search domains and the ndots setting decide how many queries actually leave the pod before the right one does. CoreDNS answers from Service and EndpointSlice state it watches from the API. The client opens a connection to the cluster IP. The node's data plane rewrites the destination to one of the ready pod IPs. The packet crosses the interface that CNI created, into the namespace the sandbox anchors, and arrives at your process — which has been listening since stage eleven.

[16 Where each failure actually lives]
This is why the spine is worth memorising. Pod Pending? You never got past stage five — filtering. Compare requests against allocatable, and read the scheduler's events, which usually name the predicate that failed. Stuck in ContainerCreating with a network error? Stages eight to nine — check the runtime's logs, not the kubelet's, because the runtime executes the plugin, and check whether IPAM has run out of addresses. Running but no traffic? Stages eleven to twelve — readiness, then EndpointSlice membership, then the service selector. DNS resolves but the connection times out? Stages twelve to thirteen — check for ready backends first, then hit a pod IP directly to separate Service translation from the workload. Same symptom class, four different subsystems.

[17 The spine]
So: desired object, admission and storage, watch and cache, controller queue, scheduler queue and binding, kubelet, CRI, CNI, CSI, EndpointSlice, service, DNS, data plane, application. Every stage asynchronous. Every stage observable. Every stage retryable. And no stage in charge of the one after it. If you can walk that spine out loud, you can place almost any Kubernetes failure on it within about thirty seconds — which is the actual skill being tested when someone asks you how Kubernetes works.
